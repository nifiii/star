# 技术设计

## 1. 背景

现有系统将采集、JSON 持久化、Express 内存查询和 React 展示放在同一项目中。

## 2. 目标

以最小改动完成成绩查询 MVP，并为错误状态和凭证安全留出明确边界。

## 3. 方案

```text
华体汇 API
   -> scripts/getToken.js 采集/规范化
   -> data/daily_matches.json + auth_config.json
   -> Express 内存缓存 /api/matches
   -> React huaTiHuiService.ts
   -> App.tsx 结果/状态展示
```

模块边界：

2026-10-22 响应式改造：仅改 React 展示、前端查询服务和样式。复用现有 API，未实现本文件中建议的后端结构化状态与数据范围改造。客户端 20 秒查询超时、两层缓存与错误透传，移除浏览器 token 前置检查。部署不迁移数据，复用原数据卷、保留旧镜像即可回滚。

- 采集层：负责登录、拉取、分页、规范化和更新时间。
- 查询层：负责筛选、排序、上限和结构化状态，不负责重新采集。
- 前端层：负责输入、展示、缓存和用户状态。
- 运维层：负责环境变量、定时更新、日志和凭证轮换。

数据模型建议：在保留 `playerA/playerB/score` 原始字段的基础上增加 `resultStatus`、`dataQuality`、`sourceUpdatedAt`。`resultStatus` 只能在多局比分完整可解析且选手身份明确时取 `win`/`loss`/`draw`，退赛、弃权、未完赛或缺少比分统一为 `pending`（界面文案为“待确认”）。

查询层必须同时执行广东省和最近一年过滤；定时采集是唯一数据更新入口，用户查询不能触发上游刷新。

权限：用户只读查询；采集凭证只在服务端环境变量或受保护配置中使用；前端禁止接触密码。

部署风险：当前 Docker/脚本架构为单容器倾向，采集任务和查询进程互相影响；本期不做拆分，只要求采集失败不伪装为空数据。

## 4. 风险

- 数据文件和内存缓存无版本校验，更新过程中可能读到半写文件，需要原子写入或临时文件替换。
- 外部 API 限流和字段变化会导致部分成功，必须保留可观测日志和更新时间。
- 任何生产写操作、凭证轮换和数据清理都应单独审批，不纳入本期自动化。
