# 前端实现设计

## 1. 背景

现有入口为 `App.tsx`，查询服务位于 `services/huaTiHuiService.ts`，类型位于 `types.ts`。

## 2. 目标

在现有结构内完成比赛历史 MVP，减少重构范围并保持现有缓存、日志和认证状态行为。

## 3. 方案

- 路由：继续使用现有 `PLAYER_HISTORY` / `DASHBOARD_RANKS` 状态，顶部双入口切换，不引入路由库。
- 组件：复用 `ConfigPanel`；将结果表格和统计逻辑保持在现有页面，系统状态日志面板已移除。
- 状态：保留查询配置、查询状态、进度、结果和选中运动员；日志只输出到浏览器控制台。
- API：调用 `GET /api/matches`，参数为 `playerName`、`playerGender`、`gameKeywords`、`province`、`city`。
- 数据处理：兼容既有 `data` 响应，由 `matchResult.ts` 对完整数字比分保守推导；不覆盖原始比分。
- 缓存：24 小时本地缓存与 5 分钟会话缓存；新页面缓存使用 `ui_v3` 前缀，键包含全部有效筛选，清除动作同步清理两层缓存。
- 长文本：赛事名、组别和组合名完整换行；PC table-layout:fixed，手机卡片；每页 20 条，导出完整结果。
- 错误：区分 HTTP 错误、无结果、格式异常和网络失败；20 秒超时，保留条件后可重试。后端没有提供部分采集状态时，前端不伪造该状态。
- 查询接口无需华体汇 token；本次页面不再读取 `auth_config.json` 或在浏览器持久化上游凭证。
- 前端非目标：不在浏览器保存华体汇密码，不直接调用华体汇私有接口，不实现后台采集调度。

## 4. 风险

- 服务函数已改为抛出可读错误，空结果仅用于 HTTP 200 的合法空数组。
- 前端不再注入 Gemini API Key，也不再拦截 `window.fetch`。
