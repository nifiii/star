# Star 响应式页面改造

## 1. 背景

Gemini 与系统状态面板已下线。原页面仍保留多色装饰、大侧栏、固定 400px 结果区与手机横向表格，压缩了查询和阅读空间。

## 2. 目标

- 面向家长和教练保留「运动员战绩」「赛事成绩」两个入口。
- 输入仍为姓名、性别、城市、赛事关键词，以及成绩查询的组别和项目；输出仍为原始比分、名次和可导出的结果。
- 成功标准：360/390/768/1440px 无页面横向溢出；PC 宽表格、手机卡片；查询、跳转、缓存、分页、导出可用；空数据与错误明确区分。

## 3. 方案

- 技术：沿用 React、TypeScript、Vite、CSS 和 lucide-react，不增加框架或路由库。
- 数据流：顶部入口 → 查询表单 → 原 `/api/matches` 或 `/api/rankings` → 状态/缓存 → 统计与结果 → Excel。浏览器只查询服务端，不触发上游采集。
- 页面：1200px 内容最大宽度；顶部品牌及双入口，下方标题、横向筛选、结果统计和结果区。去掉漂浮装饰、固定高度和重阴影。
- 视觉：深绿强调色、灰白背景、16px 中文系统字体、8px 间距节奏、12~20px 圆角；文本和颜色共同表达胜负。
- 响应式：≥900px 横向表单、成绩表格；<900px 对阵/成绩卡片，表单折行；≤600px 单列输入与双列简短筛选，触控目标至少 44px。
- 状态：首次进入引导；加载时禁用表单并显示进度；空结果提供调整建议；HTTP/网络错误展示可重试提示；成功显示当前结果筛选快照，不能用编辑中的条件冒充结果条件。
- 行为：每页 20 条，翻页回到结果标题；导出包含全部已查询记录；姓名/组合/赛事完整换行；排名按实际名次着色；原始比分始终按选手 A/B 顺序展示。
- 比分：沿用已确认规则，仅对完整数字比分计算胜负；0:0、平分、异常文字和缺失比分显示待确认；多局按局数判定，待确认不计入胜率。
- 缓存：保留 24 小时浏览器查询缓存，键包含全部筛选；清除时同步清除会话缓存；不再让上游 token 是否存在阻挡不需要 token 的本地查询接口。

| 任务 | Outcome / Scope | Inputs / Acceptance | Freedom / Dependencies |
|---|---|---|---|
| UI-01 | 统一导航、表单、状态和响应式样式 | 本文、既有 API 契约；键盘及窄屏可用 | 可决定内部 CSS 和布局；无依赖 |
| UI-02 | PC 表格、手机卡片、分页和导出 | 原有比分/排名字段；完整展示长字段、查询排名可进入战绩 | 复用现有页面状态，无新路由；依赖 UI-01 |
| UI-03 | 验证与交付 | 构建、比分规则测试、桌面/手机浏览器主路径与失败路径 | 测试样本只用虚构姓名；依赖 UI-01/02 |

验收示例：单局 `21:15`、多局 `21:15,18:21,21:19`、`0:0`、弃权、空比分；双打完整组合；长赛事名；401/500/断网；空姓名原地校验；分页后切换查询回首页；导出总量等于完整查询数量。

## 4. 风险

- 不修改 Express、采集、存量数据、定时任务或线上出口网络；上游采集超时仍需单独处理。
- 前端服务函数必须透传 HTTP/网络错误，否则错误会被误显示为空结果；这属于此次可见状态修正。
- 只对可解析比分给出胜负，无法仅凭数字推断退赛和赛制。结果不能自动确认同名者身份。
- 保留既有查询默认值与筛选含义；不改服务端项目关键词匹配逻辑。
- 如需上线，构建独立镜像、保留数据卷和旧镜像；失败时切回旧镜像，无数据迁移。
